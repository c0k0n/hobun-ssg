# clworkersvite — Pure SSG on Cloudflare

A static site pre-rendered from a [Hono](https://hono.dev) app at build time, served from Cloudflare's edge via Workers Static Assets. Bun only — no npm/npx/pnpm anywhere.

## How it works

- `src/index.tsx` only wires routes; each page is a JSX component under `src/pages/` (`HomePage`, `AboutPage`, `NotFoundPage`), composed from `src/components/` (`Layout`, `Card`).
- [`@hono/vite-ssg`](https://github.com/honojs/vite-plugins/tree/main/packages/ssg) runs the app through Hono's [`toSSG`](https://hono.dev/docs/helpers/ssg) during `vite build`, writing one real HTML file per route to `dist/`.
- Dev mode (`bun run dev`) instead runs the app live in the workerd runtime via the [Cloudflare Vite plugin](https://developers.cloudflare.com/workers/vite-plugin/) — nothing is pre-rendered until you build.
- `wrangler deploy` uploads `dist/` as [Workers Static Assets](https://developers.cloudflare.com/workers/static-assets/); pages are served directly from the edge CDN, never hitting server-side code. The bundled Worker only acts as the fallback for paths that don't match an asset (the 404 page).
- Styling uses [`hono/css`](https://hono.dev/docs/helpers/css) (`css`, `cx`, `Style`): component styles are emitted once, scoped per page — each route only ships the CSS its components actually use (verified: `dist/404.html` includes only 404 styles). True globals (`:root` variables, reset, `body`, focus styles, `prefers-reduced-motion`) stay in `src/styles/global.css`, inlined once into every page. `public/` holds only the favicon, `_headers`, and `robots.txt`; zero extra requests at runtime.
- Pages are SEO/accessibility ready: doctype, `lang`, per-page `<title>` + meta description + meta `robots`, `rel="canonical"` and self-referencing `hreflang` alternates (en + x-default) built from `SITE_URL` in `src/site.ts`, Open Graph meta, a skip link, `<main>` landmark, nav list with `aria-current`, descriptive link text, `:focus-visible` styles, and in-text links are underlined (distinguishable without relying on color). The 404 page is marked `noindex` both via `<meta name="robots">` and `X-Robots-Tag` (`_headers` + Worker).
- `public/robots.txt` allows crawling, lists the sitemap, and documents the policies; `sitemap.xml` is emitted into `dist/` by a small Vite plugin (`sitemap()` in `vite.config.ts`) from `src/site.ts` on every build — with `lastmod`, `changefreq`, `priority`, and `xhtml:link` hreflang alternates — so it stays in sync with your routes.
- 404 handling is layered: `/404` pre-renders `dist/404.html` (used by Workers Static Assets with `not_found_handling: "404-page"` when no Worker is present), and `app.notFound` returns the same styled page from the Worker when a path matches no asset and no file exists — verified `404` status in dev, `bun run preview`, and `wrangler deploy --dry-run`.
- Security headers (CSP with Trusted Types, HSTS, COOP, X-Frame-Options, `nosniff`, Referrer-Policy, Permissions-Policy) are applied twice: statically via `public/_headers` for every asset served by Workers/Pages, and via the `securityHeaders` Hono middleware in `src/index.tsx` for responses generated by the Worker (dev + the 404 page). Both sources stay in sync.

## Deploying

- **Workers Static Assets (recommended):** `bun run deploy` runs `vite build` then `wrangler deploy`, uploading `dist/` as static assets. The `main` Worker is bundled and runs only for requests that don't match an asset, so it serves the styled 404 page. Validate with `bunx wrangler deploy --dry-run`.
- **Cloudflare Pages:** also works unchanged — the same `dist/` output, `_headers` support, and automatic `404.html` custom-404 handling are native Pages features. Configure the build command as `bun run build` with output directory `dist/`. Note that Pages is in maintenance; Cloudflare's official guidance is to deploy new projects to Workers Static Assets.

## Why is @cloudflare/vite-plugin in the dependencies?

It is **dev-only** — it never runs in the build or at deploy time. It exists solely so `bun run dev` serves your Hono app live in the workerd runtime with HMR, matching production behavior (including the 404 page above). Remove it and `vite` dev has nothing to serve (there's no `index.html` until you build — the plugin is what wires `src/index.tsx` into the Vite dev server). If you'd rather have zero framework plugins, drop it and use `@hono/vite-dev-server` (also official Hono) as a plain middleware-based dev server, or just use `bun run build && bun run preview` as your loop — but you lose hot reload and the workerd environment (bindings, runtime APIs).

## Commands

```sh
bun install            # install dependencies
bun run dev            # live Hono app in workerd (HMR)
bun run build          # pre-render all routes to static HTML in dist/
bun run preview        # serve the built dist/ in workerd via wrangler dev (real 404s, _headers applied)
bun run deploy         # build + upload static assets to Cloudflare
bun run cf-typegen     # regenerate worker types (after changing wrangler.jsonc)
```

> `bun run preview` intentionally uses `wrangler dev`, not `vite preview`: Vite's preview server is a plain static file server that returns an empty `404` body and ignores `_headers`/`404.html`, so it would silently hide both the custom 404 page and the security headers. `wrangler dev` runs the actual deployment shape (assets routing + Worker fallback) locally.

> `vite` and `wrangler` are executed through bun's script runner. Do **not** add the `--bun` flag: forcing the Bun runtime on `vite build` makes `@hono/vite-ssg`'s internal server never close its WebSocket handle, so the process hangs.

## Adding a page

Add a page component under `src/pages/` and wire the route in `src/index.tsx`:

```tsx
// src/pages/AboutPage.tsx
export function AboutPage() {
  return (
    <Layout title="About" description="..." active="about">
      <h1>About</h1>
    </Layout>
  )
}

// src/index.tsx
app.get('/about', (c) => {
  return c.html(<AboutPage />)
})
```

Build and you'll get `dist/about.html`. For dynamic routes use `ssgParams`; for routes you don't want pre-rendered use `disableSSG` (see [Hono SSG docs](https://hono.dev/docs/helpers/ssg)).

## Why was the build "stuck"?

`bun --bun run build` (previously used by `preview`/`deploy`) forces vite onto the Bun runtime. The `@hono/vite-ssg` plugin starts an internal Vite server to run your app and never closes its WebSocket under Bun, so the process hangs after the files are written. Removing `--bun` fixes it — bun still installs everything and runs every script.
